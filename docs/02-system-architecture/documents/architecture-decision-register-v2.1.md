## Status model

## ADR-0001 — Invitation-bound guest email OTP

`decision_status: APPROVED` (explicit user approval: “Guest authentication: Email OTP only”); `implementation_status: PARTIALLY_READY`; `release_status: GATED`. The identity-resolution and OTP/session parameters described below are proposals/open details, not additional product approvals.

**Status:** Accepted. **Context:** API v1.0 describes phone OTP and a wedding access code, while UI/UX v5.0 describes invitation-linked email OTP. **Decision:** email OTP only; opaque invitation token resolves the intended wedding and guest. OTP proves control of the invited email channel, not legal identity. Shared-email identity resolution is proposed, not approved; see the technical policy register. Guest session is distinct, wedding/guest scoped and invalidated by logout, invitation expiry/revocation, guest-access revocation or security action. Challenges are single-use, hashed, replay-protected and rate-limited. OTP expiry, resend thresholds, attempt thresholds and absolute/idle session duration are not numerically specified and remain owner approval/configuration items. Recovery must re-run the invitation-bound verification; no email change recovery is specified. **Alternatives:** phone OTP; shared access code; email+phone. **Consequences:** guest email must be available on the invitation/guest record; the proposed invitation-context resolution must be reviewed before implementation. **Security/operations:** enumerate-resistant responses, channel-specific abuse limits, redacted logs, challenge invalidation and session revocation audit. **Affected:** PRD v2.1 addendum, API doc/OpenAPI, auth sequence/guest workflow, guest-auth module, invitation/guest/session schemas, UI guest portal. **Open:** approve numeric OTP/session thresholds and exceptional recovery procedure.

## ADR-0002 — Brevo email delivery adapter

`decision_status: APPROVED` (explicit user approval: “Email provider: Brevo”); `implementation_status: PARTIALLY_READY`; `release_status: GATED` pending sender configuration and deliverability.

**Status:** Accepted. **Context:** architecture v2.0 leaves OTP delivery provider open; UI v5.0 and owner approval name Brevo. **Decision:** Brevo is the approved provider for guest email OTP; use for other transactional email remains to be confirmed. Domain logic calls an internal email-delivery port; provider SDK/API, credentials and templates stay behind infrastructure adapter. Secrets are injected from deployment secret storage, never source control/browser. **Alternatives:** provider-neutral with no provider selection; direct Brevo calls from domain modules. **Consequences:** deployment setup requires credentials, verified sender/domain and deliverability checks; none are asserted complete. **Security/operations:** bounded timeout, safe retry for provider transient errors using stable message/challenge idempotency, no retry of permanent recipient/configuration errors, dead-letter/alert after configured policy, delivery status and provider correlation logged without OTP/body/secret. No OTP delivery retry may extend challenge expiry or create multiple valid codes. **Affected:** architecture, infrastructure diagram, PRD/auth, email adapter, worker/queue and configuration docs. **Open:** exact retry schedule, sender identity, deliverability and secret manager deployment remain operational decisions.

## ADR-0003 — Razorpay UPI-only Shagun

`decision_status: APPROVED` (explicit user approval: “Shagun provider: Razorpay, UPI only”); `implementation_status: PARTIALLY_READY`; `release_status: GATED` pending tested integration, account configuration and applicable compliance/legal review.

**Status:** Accepted. **Context:** historical PRD/architecture call provider open; UI v5 and owner approval select Razorpay. **Decision:** server-side intent/order initiation through Razorpay with UPI-only checkout. Verify signatures and webhooks server-side; use idempotency, replay prevention and provider-event deduplication. Verify amount, INR currency, intent and approved wedding recipient before recording verified success. Persist pending, successful, failed and reconciliation-required states; client redirect/screenshot/manual reference is never proof. Refunds/reversals and reconciliation are required where supported by the approved workflow; unsupported provider operations must fail explicitly and be handled through documented operational escalation, not fabricated success. The platform does not hold funds. **Alternatives:** provider-neutral, other provider, client-reported UPI. **Consequences:** separate payment adapter, webhook inbox, ledger/reconciliation, failure handling and operational alerting. **Security/operations:** secret isolation, raw-body signature verification, event deduplication, audit and reconciliation. **Affected:** Shagun API/data/workflow, UI, deployment/provider configuration, finance. **Open/release gates:** provider account and UPI enablement, production configuration, legal review, compliance verification, refund capability and reconciliation runbook. This decision does not assert Razorpay feature availability or legal compliance.

## ADR-0004 — Canonical REST prefix `/v1`

`decision_status: APPROVED` (explicit user approval: “Canonical API prefix: `/v1`”); `implementation_status: READY`; `release_status: GATED` on deployment configuration and contract checks.

**Status:** Accepted. **Context:** architecture v2.0 uses `/api/v1`; API docs/OpenAPI use `/v1`. **Decision:** `/v1` is the only canonical NestJS REST prefix. Nest global prefix, OpenAPI paths/server, API examples and BFF upstream paths must align; no `/api/v1` competing contract. Public browser URLs are BFF routes and must not be confused with upstream API prefix. **Alternatives:** `/api/v1`; version in hostname. **Consequences:** update source diagrams/docs and retain old snapshots labelled historical. **Affected:** API, architecture docs/diagrams, OpenAPI, frontend BFF integration. **Open:** deployed origin remains environment configuration.

## ADR-0005 — Next.js BFF to NestJS authority boundary

`decision_status: APPROVED` (explicit user approval: “Frontend communication: Next.js BFF → NestJS API”); `implementation_status: PARTIALLY_READY`; `release_status: GATED` pending security review of cookie, CSRF, session forwarding and origins.

**Status:** Accepted. **Context:** container diagram already shows BFF, while integrations were ambiguous. **Decision:** Browser → Next.js BFF/Route Handler → NestJS REST. Next is browser-facing transport/session boundary; Nest alone authorizes actor, resolves tenant, validates policy and executes business transitions. BFF has no domain logic or independent authorization authority. **Alternatives:** browser calling privileged Nest directly; duplicating permissions in Next. **Consequences:** server-side forwarding, explicit origin/CORS, timeout, request ID and error mapping. Use Secure/HttpOnly/SameSite cookie and CSRF defenses. BFF forwards verifiable session context; do not expose provider secrets or privileged service credentials. **Security:** Nest re-authenticates/re-authorizes each request; trusted service channel and origin validation; direct browser-to-privileged-Nest route is unsupported. **Affected:** component/container/security diagrams, API docs, web client integration, auth/session modules. **Open/proposed:** exact cookie host topology and token-forwarding mechanism need security review before implementation; recommended design is same-origin BFF cookie and server-side session forwarding without exposing upstream credentials.

## ADR-0006 — Gallery media policy

`decision_status: APPROVED` (explicit user approval: JPG/JPEG and PNG, 5 MB per file, batch caps of 5 guests / 10 co-owner-organiser); `implementation_status: PARTIALLY_READY`; `release_status: GATED` pending validated storage/processing. Dimensions and workspace quota are DEFERRED, not unresolved approvals for the selected limits.

**Status:** Accepted. **Context:** OpenAPI accepts WebP without a size cap; UI v5 has JPG/PNG, 5 MB and role batch caps, while its future-decisions section incorrectly carries 6000x6000/24MP and 5GB as recommendations. **Decision:** accept JPG/JPEG and PNG only; max 5 MB/file; per upload batch max 5 guest photos and 10 co-owner/organiser photos. WebP is rejected. Validate extension, declared MIME and file signature server-side; strip GPS EXIF; private object storage; every download authorized and short-lived; failures do not create duplicate records. Dimensions and workspace storage quota are deferred and remain UNSPECIFIED; 6000x6000, 24 MP and 5 GB are not approved. **Alternatives:** accept WebP; unrestricted uploads; promote proposed dimensions/quota. **Consequences:** byte cap encoded in OpenAPI; upload processing pipeline must inspect actual bytes. **Security/operations:** malware/content checks and safe quarantine/error policy still need pipeline detail. **Affected:** PRD/UI/API/OpenAPI/database/photo workflow/storage worker. **Open:** image dimensions, quota, retention and processing formats beyond originals require product/operational decisions. Batch counts are per individual upload batch, not lifetime.

## ADR-0007 — Governance cardinality invariants

`decision_status: APPROVED` (explicit user approval: exactly two active co-owners and one active Treasurer); `implementation_status: PARTIALLY_READY`; `release_status: GATED` pending enforcement and provisioning design.

**Status:** Accepted (business invariant); **MongoDB enforcement mechanism:** Proposed pending implementation design review. **Context:** PRD v2.0 has progressive setup; DB v1.0 permits nullable Treasurer pointer and ordinary membership role/status without cardinality enforcement. **Decision:** exactly two active co-owner memberships and exactly one active Treasurer membership are required per wedding. Setup is not operational before the second co-owner joins; use documented `SETUP_IN_PROGRESS`/`TWO_CO_OWNERS_ACTIVE` vocabulary where defined, and do not add a lifecycle state without approval. An active operational workspace cannot suspend/remove either owner if that would violate count. Treasurer replacement is explicit, authorized and audited; preserve applicable dual approvals. **Alternatives:** enforce in UI/count query only; allow ownerless/redundant treasurer states. **Proposed technical consequence:** serialize governance changes per wedding using a transaction plus a conditional versioned write/guard on the wedding root (or a dedicated one-per-wedding guard document); validate current memberships and final state within the same transaction, then update memberships, finance settings and audit/outbox. A partial unique index on active Treasurer per wedding prevents duplicates but cannot enforce exact owner count. Transaction retries must re-read/revalidate; idempotency keys prevent duplicate transitions; failure leaves all writes rolled back. Provision the first owner in setup and invite the second owner; operational actions remain disabled until both are active. Initial assignment of exactly one Treasurer during setup is unspecified and blocks workspace provisioning details; dual approval may require both co-owners, so no bootstrap bypass is invented. **Security/operations:** all membership transitions audited; concurrency/race/retry/partial-failure tests. **Affected:** PRD, membership/workspace schemas, indexes, invitation/lifecycle workflows, API operations, permissions. **Open:** technical design review is needed for the transaction/guard mechanism; owner approval is needed for unresolved provisioning and transition policy.

## ADR-0008 — Member authentication and co-owner invitation policy

`decision_status: APPROVED`; `implementation_status: NOT_STARTED`; `release_status: GATED` pending security design, provider configuration, implementation and verification.

**Decision:** Google member sign-in uses Authorization Code + PKCE through the Next.js BFF; validate state, nonce and PKCE and never expose provider credentials/tokens to the browser. Member access tokens last 15 minutes; refresh tokens have a seven-day inactivity lifetime, rotate on refresh, and token-family reuse revokes the family. Production cookies are Secure/HttpOnly; unsafe requests use synchronizer-token and Origin validation. Support current-session logout and sign-out-all. An existing account must be authenticated and the user must explicitly confirm before a Google identity is linked; matching email alone never links accounts. Brevo is the adapter provider for member verification and password-reset email; member invitees complete normal member verification, distinct from guest OTP. Co-owner invitations are dedicated, fixed-role (`CO_OWNER`), exact-email, seven-day, single-use records with no client role/scope grant. **Affected:** BFF/auth, session and email adapters, user/provider identity/session records, co-owner invitation workflow, API/OpenAPI and member UI. **Open:** cookie attributes/topology, session-family persistence and concurrent-refresh mechanics, synchronizer-token transport, BFF-to-Nest forwarding, Google deployment/client configuration, account-link recovery, and detailed sign-out-all transport/contract.
