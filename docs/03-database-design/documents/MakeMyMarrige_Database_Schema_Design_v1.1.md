# MakeMyMarrige Database Schema Design v1.1 — Reconciliation Addendum

**Base:** `MakeMyMarrige_Database_Schema_Design_v1.0.md` remains preserved. All v1.0 collections/fields continue except where this addendum explicitly specifies an amendment. This addendum is the current schema authority for these amended areas; it does not claim a generated Mongoose implementation.

## Guest OTP and session records

The v1.0 `invitations` collection represents workspace membership invitations and is not a guest invitation. A separate guest-access record is required by the invitation-linked guest model. The proposed `guestAccessInvitations` fields are `weddingId`, `guestId`, `invitedEmailNormalized`, `tokenHash`, `status`, `expiresAt`, `createdBy`, `acceptedAt?`, `revokedAt?`, `createdAt`, `version`; token hashing and exact lifecycle/status design remain proposed pending policy approval. This record is distinct from per-function visibility records. Shared-email resolution is not approved; see technical policy register v1.0. Guest-specific issue/re-send/revoke and expiry policy remain unspecified.

Proposed challenge/session records may include `guestOtpChallenges` and `guestSessions` with invitation, guest and wedding references, hashed credentials, expiry/revocation metadata and versions. Do not persist plaintext OTPs or session tokens. Numeric attempt/resend/expiry thresholds and exact invalidation/session lifecycle are not approved; TTL cleanup alone cannot enforce validity. Member authentication/session records remain separate from guest authentication. See technical policy register v1.0 before treating proposed fields or transitions as final schema requirements.

## Task ownership and dependencies

Extend `taskAssignments` with `isResponsible:boolean` (default false). At most one active responsible assignment per `(weddingId, taskId)` is enforced by a partial unique index where `status=ACTIVE AND isResponsible=true`. The selected responsible membership must also be an active assignment and active same-wedding membership; enforce transactionally when assignments change. API property is `responsibleMembershipId`; persistence may retain the relationship as this single boolean marker. Keep task dependency edges as tenant-scoped records with unique `(weddingId, taskId, dependencyTaskId)`, reject self-edges/cycles, and version-check the parent task when replacing/clearing dependencies. Serialize dependency edge changes and completion validation through a wedding-scoped `taskDependencyGraphState` guard/revision so two concurrent edge writes cannot introduce a cycle and completion cannot race a changed prerequisite graph. Each mutation increments the guard revision in the same transaction as edge/task writes; stale attempts re-read and revalidate. Completion validates every prerequisite complete in the same wedding under this serialization boundary.

## Governance cardinality and atomic transitions

The operational-state invariant is exactly two active `CO_OWNER` memberships and exactly one active Treasurer per wedding. Store/retain a single `weddingFinanceSettings` record as authoritative Treasurer pointer; require its pointed membership to be active and have the required Treasurer authority. A unique partial index on active Treasurer membership by `weddingId` is an additional at-most-one guard where supported; it cannot enforce exactly two co-owners. Proposed safe enforcement: in one MongoDB transaction, conditionally update the wedding root using its current `version`/governance revision (or a dedicated one-per-wedding guard row), read current active memberships, validate final counts and state, apply membership/settings changes and append audit/outbox. Concurrent writers contend on the same guard/root and retry from fresh state. Never rely on a count query or UI validation alone. First owner may exist during setup; operational actions are gated until second co-owner accepts. Removal/suspension that reduces active owner count below two is rejected. Treasurer transition is explicit and audited; dual approval is preserved where policy applies. Exact enum/transition implementation requires architecture review, not a new lifecycle state by assumption.

## Photo constraints

Source type allowlist is `image/jpeg` and `image/png`; maximum 5 MB (5,000,000 bytes) per photo; batch limits are 5 for guests and 10 for co-owners/organisers. Validate actual file signature and decoded media server-side; persist verified MIME/byte size/checksum; `exifStripped=true` only after successful GPS metadata removal. Store object keys privately and issue authorized short-lived downloads. Dimensions and wedding storage quota have no approved limit and must not be persisted as fixed policy. Reject/quarantine partial or invalid uploads and make completion idempotent.

## Digital Shagun payment records

`shagunPaymentIntents` records the approved provider (`RAZORPAY`), method (`UPI`), wedding/guest scope, `amountPaise`, `currency:INR`, recipient configuration version/reference, hash of the internal idempotency key, provider references when returned, current state, timestamps and version. State categories are `PENDING`, `SUCCESSFUL`, `FAILED` and `RECONCILIATION_REQUIRED`; `REFUNDED`/`REVERSED` may be recorded only after provider-verified outcomes where supported. Never mark success from a browser redirect or user evidence. Keep provider event inbox records keyed uniquely by provider plus provider event ID; retain signature verification result/time, received/processed state and a safe correlation reference. Verify amount/currency/intent/recipient before atomically updating contribution state and audit/outbox. Reconciliation reads provider state outside transactions and commits an idempotent verified result. Do not store credentials or sensitive webhook secrets in documents. Refund request/approval policy and provider checkout handoff schema remain blocked/unspecified; do not invent either.

## Status and lifecycle

OTP challenge/session lifecycle and gallery policy above supersede conflicting v1.0 fields/assumptions. Existing `SETUP_IN_PROGRESS` and `TWO_CO_OWNERS_ACTIVE` lifecycle vocabulary remains; no new lifecycle enum is introduced. Support recovery remains modeled via `supportRecoveryCases`, but actor, approval and public/internal API are unresolved; do not add a privilege field or endpoint until approved.

## Milestone 2.1 — implemented identity and workspace persistence baseline

This section amends the v1.0 catalogue only for the implemented persistence collections below. It records the implementation boundary; it does not approve any authentication provider flow, browser session, email delivery, HTTP operation, or governance bootstrap.

### `users` and `providerIdentities`

`users` is a global identity collection, independent of a wedding. Its implemented fields are `emailNormalized` (trimmed/lower-cased), `emailVerificationStatus` (`UNVERIFIED|VERIFIED`), `emailVerifiedAt?`, `displayName`, `passwordHash?` (not selected by default), `accountStatus` (`ACTIVE|SUSPENDED|CLOSED`), timestamps and optimistic `version`. A validation rule requires `emailVerifiedAt` to be present exactly when the verification status is `VERIFIED`. `emailNormalized` has a unique index.

This implementation replaces the v1.0 `authProviderLinks` embedded-array representation with a separate `providerIdentities` collection, avoiding an unbounded user document and making the global provider-subject constraint enforceable. Each record has immutable `userId`, `provider`, stable immutable `providerSubject`, `linkedAt`, timestamps and version. The unique `(provider, providerSubject)` index prevents one external identity from linking to more than one user; `(userId, provider)` is indexed for account-link lookup. Linking authorization and collision/recovery behavior are not implemented in this milestone.

### `weddings`, `weddingMemberships`, and `membershipPeriodEvents`

`weddings` is the tenant root. Implemented fields are `name`, optional `coupleNames`, `primaryCity`, optional `description`, date-only `weddingDate`, `timezone`, `lifecycleStatus`, `createdByUserId`, optional `deletionDueAt`, timestamps and optimistic `version`. The supported persisted lifecycle vocabulary is `SETUP_IN_PROGRESS|TWO_CO_OWNERS_ACTIVE|ACTIVE|POST_WEDDING|CANCELLED`. This records all active source vocabulary without inventing transition rules.

`weddingMemberships` has immutable `weddingId` and `userId`, `memberType` (`CO_OWNER|ORGANISER|TREASURER`), `status` (`ACTIVE|SUSPENDED|ENDED`), `joinedAt`, optional `endedAt`, timestamps and optimistic `version`. The unique `(userId, weddingId)` index makes one durable membership record the source of truth for a user/wedding pair; a rejoin reactivates that record instead of creating another. The partial unique `userId` index for `ACTIVE|SUSPENDED` enforces the approved one-occupied-membership-slot rule. The partial unique active-Treasurer `weddingId` index is an at-most-one guard, not proof of the exact-one invariant. `membershipPeriodEvents` is append-only and stores immutable membership event records, indexed by `(weddingId, membershipId, occurredAt, _id)` so period history is read in bounded pages rather than embedded unboundedly.

### `invitations` — co-owner invitation records

The implemented co-owner invitation records use the existing `invitations` collection and fixed `role:CO_OWNER`, which distinguishes them from future guest-access invitations. They store `weddingId`, exact `invitedEmailNormalized`, a SHA-256 `tokenHash` only, `expiresAt`, status (`PENDING|ACCEPTED|REVOKED|EXPIRED`), `createdByMembershipId`, optional acceptance/revocation metadata, timestamps and optimistic `version`. An `ACCEPTED` record requires both accepting user and acceptance time; every other state rejects acceptance metadata. A 256-bit opaque token is generated only for delivery and immediately hashed; raw tokens are never a persistence field. `tokenHash` is unique; `(weddingId, invitedEmailNormalized, status)` and `(weddingId, status, expiresAt)` support tenant-scoped, paged review and expiry checks. A TTL index is deliberately absent: expiry must be enforced by the conditional operation, not asynchronous deletion.

### Transaction and invariant boundary

Workspace creation with its initial membership and `JOINED` event is one MongoDB replica-set transaction. Rejoin/reactivation must conditionally transition the existing `ENDED` membership and append its history event in the same transaction. Invitation acceptance must condition on `status=PENDING` and `expiresAt > now`, then atomically consume the invitation with any membership/history/audit writes required by the future invitation workflow; this milestone persists the state and validates this conditional single-use pattern but exposes no workflow or HTTP operation.

Exactly two active co-owners and exactly one active Treasurer remain approved operational invariants. This milestone intentionally adds no bootstrap bypass and does not claim that an index can enforce a cross-document exact count. The governance milestone must serialize membership and Treasurer changes through a conditional wedding-root version or per-wedding guard in a transaction, validate final counts, update the Treasurer setting, and append audit/outbox records atomically. Lifecycle transition authorization, Treasurer appointment/replacement, invitations issuance/acceptance authority, and account-link collision policy remain unresolved outside this persistence baseline.

## Proposed member-session persistence design

This section designs the approved 15-minute access / seven-day inactivity refresh policy; it does not implement a schema. Keep `memberSessionFamilies` separate from `memberRefreshSessions`. A family has immutable opaque `familyId`, `userId`, `status:ACTIVE|REVOKED`, creation/revocation/reuse timestamps, revocation reason, and timestamps/version. A refresh-session record has immutable opaque `sessionId`, `familyId`, `userId`, SHA-256 `refreshTokenHash` only, `status:ACTIVE|ROTATED|REVOKED|EXPIRED`, `issuedAt`, `lastUsedAt`, `expiresAt`, `rotatedAt?`, `replacedBySessionId?`, revocation/reuse metadata, a hashed CSRF synchronizer token for the active session, and timestamps/version. Never persist raw refresh/access/CSRF tokens or provider tokens. Required indexes are unique `familyId`, unique `refreshTokenHash`, unique `sessionId`, `(userId,status,expiresAt)`, and `(familyId,status,expiresAt)`; retention/TTL of revoked session/audit records is an operational decision and must not erase reuse evidence prematurely.

Initial sign-in creates one family and one active refresh session in a transaction and emits an audit/outbox event. Refresh hashes the presented cookie token, conditionally changes exactly one active/unexpired row to `ROTATED`, creates its replacement active row, updates family activity, and emits audit/outbox in the same replica-set transaction. If no active row matches and the hash identifies a previously rotated/revoked token, revoke the whole family transactionally and audit `REFRESH_TOKEN_REUSE`; require reauthentication. Expired/revoked credentials return generic 401 and never disclose token state. Current logout revokes its active refresh session; sign-out-all revokes every active family for the authenticated user in one transaction. Access tokens are short-lived bearer/session artifacts: they are not guaranteed to be immediately invalidated by sign-out unless a future access-token denylist/introspection design is approved.

The BFF may single-flight requests within one process, but that cannot coordinate browser tabs, process restarts, or multiple BFF instances. MongoDB conditional update plus transaction is the final security guard: one simultaneous refresh wins, and a delayed old-token request is reuse that revokes the family. A browser-side cross-tab coordinator and a distributed BFF lock keyed by the refresh-session identity are required to reduce legitimate races, but neither weakens the final NestJS conditional check or creates a grace window. Requests arriving during an in-progress refresh wait for its BFF result where that coordination is available; success propagates replacement cookies and failure clears them. A network failure after Nest rotates but before BFF receives the response leaves the browser with the old token; retrying it triggers reuse and requires authentication again. Transaction retry repeats only before an outcome is committed; after commit, retrying the same old token is reuse. The distributed lock/store selection, lock expiry/fencing, cross-tab protocol, and user experience for this security trade-off remain implementation design. Account linking uses the existing unique `(provider,providerSubject)` record: authenticate the current user, verify the Google subject through the BFF OAuth flow, require explicit confirmation, then transactionally insert the identity and audit. Duplicate-key collision means another account owns the subject; do not disclose that account or auto-merge. Recovery/transfer of a linked identity remains unresolved.
